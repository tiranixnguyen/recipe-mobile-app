Sổ tay người mới

Mọi thứ bạn cần để nhận việc đầu tiên trong dự án Bếp Hoà Lạc: thuật ngữ, công cụ, cách đọc dự án, cách nhận issue, code với AI agent, mở PR và dùng Slack. Đọc một lượt khoảng 20 phút, sau đó giữ làm bảng tra cứu.

1Tóm tắt 1 phút

Bếp Hoà Lạc là app Android gợi ý món ăn cho sinh viên khu Hoà Lạc từ đồ đang có trong tủ và dụng cụ trong phòng, rồi lên thực đơn ngày/tuần và danh sách đi chợ. Nhóm 5 người làm MVP trong 4 tuần, 19/10 → 15/11/2026.

Luật sản phẩm

  • Không hiển thị giá tiền ở bất kỳ đâu.
  • Chỉ Android.
  • Không tài khoản: mọi dữ liệu nằm trên máy người dùng.
  • Công thức đóng gói sẵn, app chạy offline.

Cách nhóm làm việc

  • Mỗi người một feature, một thư mục riêng.
  • Mỗi việc là một issue trên GitHub.
  • Code cùng AI agent (Antigravity), nhưng bạn chịu trách nhiệm từng dòng.
  • Mọi thay đổi vào main qua PR: CI xanh + Lead duyệt.

Ai phụ trách feature nào: xem cột Assignee trên Project Recipe MVP.

2Ngày đầu tiên

  • Nhận lời mời vào repo trên GitHub (kiểm tra email hoặc trang lời mời).
  • Cài đủ công cụ ở mục 3.
  • Clone repo và chạy app (xem lệnh bên dưới).
  • Chạy thử app demo trên nhánh demo và đọc docs/demo-flow.md ở nhánh đó.
  • Đọc dự án theo thứ tự ở mục 6.
  • Vào Slack (#dev, #ci, #standup) và gõ /github signin, hoặc bật thông báo GitHub nếu bạn không dùng Slack (mục 10).
  • Nhận một bài tập khởi động (issue có label exercise) và làm trọn một vòng issue → PR → merge.
# Clone và chạy lần đầu
git clone https://github.com/tiranixnguyen/recipe-mobile-app.git
cd recipe-mobile-app
fvm install                 # cài đúng Flutter theo .fvmrc
fvm flutter pub get
fvm flutter doctor          # kiểm tra môi trường, sửa hết dấu ✗ phần Android
fvm flutter run             # chạy trên emulator hoặc điện thoại đang cắm

# Xem app demo (menu trà sữa) để hiểu cách tổ chức code
git switch demo && fvm flutter pub get && fvm flutter run
git switch main

5Thuật ngữ

Git & GitHub

Repo
Kho chứa toàn bộ code dự án: tiranixnguyen/recipe-mobile-app.
Branch (nhánh)
Một bản làm việc tách riêng. main là app thật; demo là app minh hoạ; mỗi issue bạn làm trên một nhánh mới như feat/23-search.
Commit
Một lần lưu thay đổi, kèm câu mô tả.

Đẩy commit của bạn lên GitHub / kéo thay đổi mới nhất về máy.
Issue
Một việc cần làm, có mô tả và tiêu chí hoàn thành. Mỗi issue có số, ví dụ #23.
Label
Nhãn phân loại issue: feature:discover, P0, size:M…
Milestone
Mốc theo tuần: W1 · Nền tảng & component … W4 · Kiểm thử & phát hành.
Assignee
Người đang làm issue đó.
Project (board)
Bảng Kanban gom mọi issue: Todo → In Progress → Done.
PR (Pull Request)
Đề nghị gộp nhánh của bạn vào main. Nơi diễn ra CI và review.
Review / Approve
Người khác đọc PR, góp ý; khi ổn thì Approve (duyệt).
Merge
Gộp PR vào main. Viết Closes #23 trong PR thì issue tự đóng khi merge.
Conflict
Hai người sửa cùng chỗ một file, Git không tự gộp được — phải sửa tay.
Rebase
Đặt các commit của bạn lên trên bản main mới nhất (cách xử lý conflict nhóm dùng).
CI
Máy chủ GitHub tự chạy format · analyze · test trên mỗi PR. Đỏ = chưa merge được.
CODEOWNERS
File quy định thư mục nào thuộc ai; PR đụng vào thư mục của người khác sẽ cần người đó duyệt.
Branch protection
Luật của main/demo: không push thẳng, phải qua PR có CI xanh và 1 approval.

Tìm việc của bạn

  • Mở Project Recipe MVP → view Việc của tôi, hoặc lọc assignee:@me.
  • Terminal: gh issue list --assignee @me.
  • Việc chung (nhập công thức, test với sinh viên, bug bash) có label shared — ai cũng tham gia.

Đọc một issue

② Acceptance criteria — làm đủ từng ô mới là xong:

  • Tìm theo tên món và nguyên liệu, không phân biệt dấu…
  • Chip lọc: thời gian, dụng cụ, bữa, chế độ ăn…

③ Phụ thuộc → issue phải xong trước (hoặc đã có stub).

Label

người làm

Chọn issue nào làm trước

  1. Thuộc milestone tuần hiện tại.
  2. P0 trước P1.
  3. Các issue Phụ thuộc đã xong, hoặc đã có stub để dùng tạm.
  4. Issue có tên …-00 (component + public API) luôn làm đầu tiên vì người khác chờ.

Chọn xong: kéo thẻ sang In Progress trên Project. Chỉ giữ một issue In Progress tại một thời điểm.

Đừng tự nhận issue của feature khác. Muốn giúp thì hỏi người đó hoặc Lead trước.

8Vòng làm một issue

Issue→Branch→Agent: plan→Bạn duyệt→ Agent: code→Tự kiểm tra→PR→CI + Claude review→ Lead approve→Merge→Issue tự đóng
  1. Lấy code mới nhất và tạo nhánh 
    git switch main && git pull
git switch -c feat/23-search       # feat/<số issue>-<mô-tả-ngắn>; sửa lỗi dùng fix/…
  2. Giao việc cho agentTrong Antigravity, dùng prompt mẫu ở mục 9. Agent sẽ đọc AGENTS.md, issue và prototype rồi đề xuất plan.
  3. Duyệt planPlan chỉ được đụng thư mục feature của bạn và test của nó. Thấy lib/core/, lib/app/, pubspec.yaml hay feature khác → từ chối, hỏi Lead.
  4. Agent code, bạn đọc lạiĐọc từng file thay đổi. Chỗ nào không hiểu, hỏi agent giải thích — đừng merge thứ mình không hiểu.
  5. Tự kiểm tra 
    fvm dart format lib test
fvm flutter analyze                # phải "No issues found"
fvm flutter test                   # phải "All tests passed"
fvm flutter run                    # bấm thử trên Android, so với prototype, chụp màn hình
  6. Commit và push 
    git add lib/features/discover test/features/discover
git commit -m "feat(discover): search by dish or ingredient"
git push -u origin HEAD
  7. Mở PRTrên GitHub bấm Compare & pull request, hoặc gh pr create --base main. Điền template: Closes #23, mô tả ngắn, ảnh chụp màn hình Android đặt cạnh prototype, tick checklist.
  8. CI và Claude reviewCI chạy trong vài phút (theo dõi ở tab Checks hoặc #ci). Claude để lại comment góp ý: mục "Cần sửa trước khi merge" thì sửa; "Gợi ý không bắt buộc" thì tuỳ bạn.
  9. Lead review và approveSửa theo góp ý: commit thêm vào cùng nhánh rồi push — PR tự cập nhật. Không mở PR mới.
  10. MergeKhi đã có approve và CI xanh, bạn bấm Merge pull request. Issue tự đóng, thẻ trên Project tự sang Done, nhánh được xoá. Quay lại bước 1 với issue tiếp theo.
PR nhỏ dễ duyệt: mỗi PR một issue, nên dưới ~400 dòng. Issue size:L thì tách thành 2 PR.

9Làm việc với AI agent

Prompt mẫu cho Antigravity

Làm issue #23 trong repo này.
1. Đọc AGENTS.md, nội dung issue (gh issue view 23) và prototype được nhắc trong issue.
2. Chỉ sửa trong lib/features/discover/ và test/features/discover/.
3. Lập plan: file sẽ tạo/sửa, test sẽ viết. Dừng lại chờ mình duyệt.
4. Code xong thì chạy fvm dart format lib test, fvm flutter analyze, fvm flutter test cho tới khi sạch.

Antigravity có workflow /implement-issue làm đúng các bước trên (đã có trên nhánh demo; lên main cùng AGENTS.md bản đầy đủ ở issue SET-05).

Agent làm tốt

  • Dựng màn theo prototype
  • Viết test, sửa lỗi analyze
  • Giải thích code, lệnh, lỗi
  • Xử lý conflict đơn giản

Bạn phải tự kiểm

  • Có sửa ngoài thư mục feature không?
  • Có mã màu cứng thay vì token không?
  • Có hiện giá tiền ở đâu không? (luật: không)
  • Chữ trên UI đúng giọng văn: xưng "bạn", không emoji
Dấu hiệu dừng agent lại: muốn thêm package, sửa lib/core/, xoá test đang có, tắt lint, hay "sửa tạm" bằng // ignore. Hỏi Lead trước.

Nếu bạn không dùng Slack

  3. Standup: comment theo đúng mẫu bên trái vào issue bạn đang làm trước 10h.
  4. Hỏi bài: comment trong issue/PR và tag @tiranixnguyen.
  5. Báo Lead một lần là bạn không dùng Slack để Lead biết tìm bạn ở đâu.
Quy tắc chung: gì liên quan một issue/PR thì viết ở issue/PR đó (để còn lưu lại). Slack dùng cho câu hỏi nhanh và nhắc nhau.

Tình huốngLàm gì
CI đỏMở tab Checks → xem bước nào lỗi. Chạy lại đúng lệnh đó ở máy (fvm dart format lib test, fvm flutter analyze, fvm flutter test), sửa, push lại.
PR báo conflict / "branch is out of date" 
git fetch origin
git rebase origin/main          # Git dừng ở file conflict
# sửa file (giữ cả hai phần nếu cần), rồi:
git add <file> && git rebase --continue
fvm flutter test
git push --force-with-lease
Không chắc thì nhờ agent: "giúp mình xử lý conflict này, giải thích từng chỗ".
Claude review góp ý saiTrả lời ngay dưới comment vì sao không sửa. Bot không chặn merge; Lead quyết.
Cần thứ ở feature khác chưa cóDùng stub trong public API của feature đó. Chưa có stub → nhắn chủ feature, ghi vào phần Phụ thuộc của PR.
Cần sửa core/, thêm packageKhông tự sửa. Comment vào issue, tag Lead.
Lỡ commit vào main ở máygit switch -c feat/<số>-<tên> (mang commit sang nhánh mới), rồi git switch main && git reset --hard origin/main. Không push được lên main đâu, đừng lo.
Kẹt quá 2 giờDừng lại và hỏi — nhắn #dev hoặc comment issue, kèm việc đã thử. Hỏi sớm rẻ hơn trễ hạn.
